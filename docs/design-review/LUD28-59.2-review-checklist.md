## 📋 Review-Checkliste

### 1. Dokumentation Vollständigkeit

#### DBM-SCHEMA-03 Finalisierung
- [ ] Alle 18 PoC-Entities vollständig definiert
- [ ] 10+ Full-Scope Entities hinzugefügt (mindestens Draft)
- [ ] Alle TypeORM-Decorators korrekt verwendet
- [ ] FK-Constraint-Namen gemäß Konventionen (`fk_[from]__[to]__[column]`)
- [ ] Index-Namen gemäß Konventionen (`ix_[table]__[column]`)
- [ ] Unique-Constraint-Namen gemäß Konventionen (`uq_[table]__[column]`)

#### Per-Entity Specs
- [ ] Auth-Entities: 3/3 Specs erstellt (User, UserRights, UserAllowedTerminal)
- [ ] Terminal-Entities: 2/2 Specs erstellt (AppTerminal, TerminalRights)
- [ ] Speech-Entities: 2/2 Specs erstellt (SpeechHumanInput, SpeechTestInput)
- [ ] Logging-Entities: 4/4 Specs erstellt (Category, IntentLog, SpeechTranscript, EventLog)
- [ ] HA-Entities: 7/7 PoC-Specs erstellt (Snapshot, Area, Device, Entity, EntityState, EntityAttribute)
- [ ] Full-Scope: Mindestens Struktur für 10+ weitere Entities

### 2. Entity-Design

#### Felder & Datentypen
- [ ] Alle PKs als UUID definiert (`@PrimaryGeneratedColumn('uuid')`)
- [ ] Natürliche Schlüssel haben UNIQUE-Constraints
- [ ] Nullable-Felder korrekt markiert
- [ ] Defaults für Pflichtfelder definiert
- [ ] ENUM-Typen für Status-Felder verwendet
- [ ] JSONB für flexible Daten (PostgreSQL) oder JSON (MariaDB)
- [ ] Timestamps (`created_at`, `updated_at`) überall vorhanden

#### Beziehungen
- [ ] Alle 1:1 Beziehungen korrekt definiert (User ↔ UserRights, AppTerminal ↔ TerminalRights)
- [ ] Alle 1:n Beziehungen mit @ManyToOne/@OneToMany
- [ ] M:N Beziehungen mit @ManyToMany + @JoinTable oder expliziter Join-Entity
- [ ] Self-Referenzen korrekt (HaDevice.viaDevice)
- [ ] @JoinColumn mit `foreignKeyConstraintName` verwendet

#### ON DELETE / ON UPDATE Verhalten
- [ ] Logging → User/Terminal: `ON DELETE SET NULL, ON UPDATE CASCADE`
- [ ] Stammdaten → Abhängige: `ON DELETE CASCADE, ON UPDATE CASCADE`
- [ ] 1:1 Rechte-Tabellen: `ON DELETE CASCADE, ON UPDATE CASCADE`
- [ ] M:N Join-Tabellen: `ON DELETE CASCADE, ON UPDATE CASCADE`
- [ ] HA-Historien: `ON DELETE CASCADE` (Snapshots → States → Attributes)

### 3. Constraints & Indizes

#### Primary Keys
- [ ] Alle Entities haben PK (`id: UUID`)
- [ ] 1:1 Entities verwenden FK als PK (UserRights.userId, TerminalRights.terminalId)
- [ ] Join-Tabellen haben zusammengesetzte PKs (`user_id`, `terminal_id`)

#### Unique-Constraints
- [ ] `users.username` UNIQUE
- [ ] `users.email` UNIQUE
- [ ] `app_terminals.terminal_id` UNIQUE
- [ ] `categories.key` UNIQUE
- [ ] HA-Entities: natürliche Keys UNIQUE (`entity_id`, `area_id`, `device_id`)
- [ ] `ha_entity_states.(entity_id, snapshot_id)` UNIQUE zusammengesetzt

#### Indizes (Performance)
- [ ] Alle FKs haben Indizes
- [ ] Timestamp-Spalten für Queries indiziert (`created_at`, `last_updated`)
- [ ] ENUM-Spalten für Filter indiziert (`status`, `type`, `role`)
- [ ] Zusammengesetzte Indizes für häufige Queries:
  - [ ] `(user_id, created_at)` für Transcripts
  - [ ] `(terminal_id, created_at)` für SpeechInputs
  - [ ] `(entity_state_id, attribute_key)` für HA-Attributes

### 4. Offene Entscheidungen

#### Datenbank-Wahl
- [ ] PostgreSQL vs. MariaDB entschieden
- [ ] JSONB vs. JSON-String dokumentiert
- [ ] UUID-Support validiert

#### Performance-Überlegungen
- [ ] EAV-Modell für HA-Attributes evaluiert
  - [ ] Alternative: JSONB-Column statt EAV?
  - [ ] Partitionierung für große Tabellen?
- [ ] Index-Strategie für Millionen Rows (ha_entity_states, ha_entity_attributes)
- [ ] Materialized Views für Statistiken?

#### Datenmigration
- [ ] Strategie Mongo → SQL dokumentiert (Follow-up Ticket LUD28-110)
- [ ] ObjectId → UUID Mapping-Strategie
- [ ] Daten-Transformationsregeln

### 5. Namenskonventionen

- [ ] Tabellennamen: `snake_case`
- [ ] Spaltennamen: `snake_case`
- [ ] Entity-Klassen: `PascalCase`
- [ ] FK-Constraints: `fk_<from_table>__<to_table>__<column>`
- [ ] Unique-Constraints: `uq_<table>__<column>`
- [ ] Indizes: `ix_<table>__<column>`

### 6. Code-Qualität

#### TypeORM Best Practices
- [ ] Alle Entities erben von `BaseEntity` (falls verwendet)
- [ ] Circular Dependencies vermieden (forwardRef() wo nötig)
- [ ] Lazy-Loading vs. Eager-Loading dokumentiert
- [ ] Repository-Pattern vs. Active-Record dokumentiert

#### TypeScript
- [ ] Alle Typen korrekt (string, number, Date, enum)
- [ ] Optional-Felder mit `?` markiert
- [ ] ENUM-Exports für Validierung vorhanden

### 7. Dokumentation

- [ ] Alle Entities haben JSDoc-Kommentare
- [ ] Komplexe Beziehungen kommentiert
- [ ] Abweichungen vom Standard dokumentiert
- [ ] Design-Entscheidungen begründet

## 🔍 Review-Punkte (Detail)

### Entity: User
- [ ] Felder vollständig (id, username, email, passwordHash, profileData, timestamps)
- [ ] Relationen: UserRights (1:1), SpeechInputs (1:n), Transcripts (1:n), EventLogs (1:n), AllowedTerminals (M:N)
- [ ] Indizes: username, email (UNIQUE)
- [ ] ON DELETE: SET NULL für Logs, CASCADE für UserRights

### Entity: UserRights
- [ ] PK ist FK zu User (userId)
- [ ] Alle Permission-Booleans vorhanden
- [ ] Role-ENUM definiert
- [ ] Status-ENUM definiert
- [ ] Relation zu User mit CASCADE

### Entity: AppTerminal
- [ ] terminal_id UNIQUE
- [ ] Type-ENUM vollständig
- [ ] Status-ENUM vollständig
- [ ] Relationen: TerminalRights (1:1), AssignedUser (n:1), SpeechInputs (1:n), AllowedUsers (M:N)

### Entity: HaEntity
- [ ] entity_id UNIQUE
- [ ] EntityType-ENUM vollständig (14 Typen)
- [ ] domain und objectId extrahiert
- [ ] Relationen: Device (n:1), Area (n:1), States (1:n)

### Entity: HaEntityState
- [ ] Unique-Constraint auf (entity_id, snapshot_id)
- [ ] ON DELETE CASCADE für Snapshot und Entity
- [ ] Indizes: entity_id, snapshot_id, last_updated

### Entity: HaEntityAttribute (EAV)
- [ ] AttributeType-ENUM (string, number, boolean, array, object)
- [ ] JSONB für attribute_value
- [ ] Zusammengesetzter Index (entity_state_id, attribute_key)
